# 学生端「AI 对话 + 课程推荐」设计

- 日期：2026-10-20
- 状态：设计已逐节确认，待审阅
- 范围：新建学生端网页版（`zhixue-student-web`），AI 服务新增会话与流式对话，课程服务新增内部接口，补 3 门 Java 种子课；后续分期移植到小程序

## 0. 背景与目标

学生端现在是微信小程序，AI 答疑只是「我的」里的一个入口页，答完就结束，和平台上的课程没有关系。

目标是把 AI 对话变成学生端的**主入口**，布局参照 Codex：

- 左侧边栏放学生端功能（课程库、我的课程、商城、订单、收藏）与「最近」对话；
- 中间是 AI 对话框；
- 学生问一个问题（如 Java 相关问题），先得到解答，**回答下方推荐平台上相关的视频课**，并标出最相关的课时，点一下就能试看或购买。

成功标准：问「HashMap 为什么线程不安全」，0.5 秒左右开始逐字出答案，答完后下方出现《Java 并发编程实战》《Java 集合与泛型》的卡片，卡片里标着「ConcurrentHashMap 原理」等课时，点击可直接播放或购买；问与课程无关的问题时不出现推荐。

## 1. 决策记录

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| D1 | 平台 | 先做网页版定型交互，再移植到小程序首页 | 手机屏放不下常驻侧边栏；网页版能完整做出 Codex 布局，接口两端共用 |

| D4 | 课程库 | 补 3 门 Java 种子课；无相关课时不推荐 | 现有上架课程里没有 Java 课，演示场景无法成立；不拿无关热门课凑数，避免广告感 |
| D5 | 侧边栏 | 现有后端能支撑的功能 + 补齐学习进度、课程评价、售后申请 | 没有后端的入口点进去是空壳，所以缺口功能要先补后端 |

### 3.3 交互

1. **新对话**：空状态显示推荐问题。第一条消息发出时才创建会话；标题取首个问题的前 20 字（去掉换行与首尾空白），不额外调用模型。
2. **流式回答**：生成时发送按钮变为「停止」。停止后保留已生成部分并标注「已停止」，该回答不出推荐。
3. **回答渲染**：Markdown + 代码高亮；规则见 6.2。
4. **推荐卡片**：回答完成后出现在回答下方，最多 3 门课，每门最多标 2 个课时。点课程进入课程详情；点课时，可播放（已购或在试看范围内）则直接播放该课时，否则弹出购买提示。没有足够相关的课程时不显示推荐区。课时前的编号（如 2.2）由前端按章节顺序与课时顺序生成，课时标题本身不含编号。
5. **限定课程提问**：从课程详情点「问这门课」进入新对话时，输入框上方显示「正在问：Java 并发编程 ×」，只检索该课程资料；发出第一条消息前可点 × 改为全部课程。**范围在会话创建时确定**：之后的提问沿用会话的 `course_id`，标签变为不可修改；想换范围就开新对话。普通进入时不显示该标签。
6. **最近**：按最后消息时间倒序；悬停出现 ⋯，可重命名、删除。
7. **窄屏**（宽度 < 960px）：侧边栏收起为左上角按钮唤出的抽屉。
8. **账号**：账号密码 + 验证码登录，复用现有 `/auth/captcha`、`/auth/login`；演示账号 `student / student123`。注册二期做：现有 `RegisterController` 对所有请求一律拒绝（「账号注册功能暂未开放」），需要补一整套注册后端，见 8 节。
9. **课程详情（一期）**：封面、标题、价格、简介、章节课时列表（锁定 / 可试看 / 已购）、「立即购买」（复用现有下单 + 模拟收银台）、「问这门课」；课时播放器在详情页内打开。

## 4. 数据流与接口（一期）

### 4.1 AI 服务新增接口

全部要求登录，只能操作本人数据；访问他人会话一律返回 **404**（不暴露会话是否存在）。

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/ai/conversations/messages` | 提问，流式返回回答与推荐；不带 `conversationId` 时自动新建会话 |
| `GET` | `/ai/conversations?pageNum=&pageSize=` | 「最近」列表，按 `last_message_time` 倒序 |
| `GET` | `/ai/conversations/{id}/messages` | 打开历史会话（推荐卡片按最新状态解析，见 4.5） |
| `PUT` | `/ai/conversations/{id}` | 重命名，body `{ title }`，1–64 字 |
| `DELETE` | `/ai/conversations/{id}` | 删除（软删除） |

用 `PUT` 而非 `PATCH`：网关 CORS 只放行 GET / POST / PUT / DELETE / OPTIONS。

### 4.2 流式事件格式

请求体：`{ conversationId?: string, question: string, courseId?: string }`。`courseId` 只在新建会话（不带 `conversationId`）时生效；已有会话一律使用会话保存的 `course_id`，请求中的值被忽略。

流开始前可判定的错误（未登录、问题为空、超过 500 字、会话不存在、已有回答在生成）以普通 JSON 返回，格式与现有接口一致：

- 业务错误经 `GlobalExceptionHandler` 返回 **HTTP 200**，错误码在 `body.code`（400 / 404 / 409）；
- 未登录或令牌失效由网关拦截，返回 **HTTP 401**，body 为 `{"code":401,"msg":"…"}`。

前端先看响应的 `Content-Type`：是 `text/event-stream` 就读流；否则解析 JSON，**以 `body.code` 为准**（不能只判断 `response.ok`）。

没有流前错误时返回 `text/event-stream`：

```
event: meta    data: {"conversationId":"…","messageId":"…","title":"HashMap 为什么线程不安全"}
event: delta   data: {"text":"HashMap 在多线程下"}                      ← 多次
event: done    data: {"sources":[{"title":"Java 集合与泛型 · HashMap 深入"}],
                      "notice":null,
                      "recommendations":[{
                        "courseId":"2007","title":"Java 并发编程实战","coverUrl":"…",
                        "price":99.00,"purchased":false,"previewable":true,
                        "lessons":[{"lessonId":"4024","chapterId":"3017",
                                    "title":"ConcurrentHashMap 原理","duration":1080,"playable":false}]}]}
event: error   data: {"code":503,"msg":"AI 服务暂不可用，请稍后再试"}
```

- 所有 ID 以字符串传输（雪花 ID 超出 JS 安全整数）。
- `notice` 仅在降级时有值（见 6.1，资料检索失败）。
- 流以 `done` 或 `error` 之一结束，二者互斥。
- 实现：AI 服务的 Spring MVC 控制器返回 `Flux<ServerSentEvent<…>>`；网关只校验查询串、不缓冲响应体，流式可直接透传（已核实 `XssFilter` 与 `AuthFilter`）。
- 流式响应带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`：以后经 Nginx 部署时，Nginx 默认缓冲代理响应，会把整段回答攒到最后才发出；这个响应头让 Nginx 对该响应不做缓冲，不需要改 Nginx 配置。

### 4.3 一次提问的处理顺序

1. **请求线程上完成同步部分，顺序固定**：
   1. 读取当前用户 ID 与是否管理员（来自网关注入的请求头，进入流式处理后读不到，必须在此取出并向后传递）；
   2. 校验参数（问题非空、≤ 500 字）；
   3. 传了 `conversationId` 时校验会话存在且属于本人（只读，不符返回 404）；
   4. **原子占位「生成中」**：同一用户已有占位则直接返回 409。**此前不写任何数据**，所以重复点击或多标签页不会留下空会话或无回答的问题；
   5. 创建会话（如需要）、保存学生消息；
   6. 开始流式输出。

   第 4 步之后、第 6 步开始之前的任何异常（如保存消息时数据库报错）都必须释放占位，再按流前错误返回；流开始之后，占位在流结束时统一释放（见 4.6）。
2. **检索问句**：当前问题 + 同一会话中上一个学生问题（用于理解「那它和 HashMap 有什么区别」这类追问）；只带上一问，避免话题漂移。
3. **一次检索两处使用**：问句向量化一次；新增 `VectorStoreService.searchWithScores(vector, topK=8, courseId)`，返回 `(chunkId, courseId, cos)` 列表：
   - 分数最高的 4 个片段作为回答的【课程资料】；
   - 全部 8 个片段按课程聚合，作为推荐候选。

   **分数一律用余弦值**：索引按 `cosine` 建立，ES 返回的 `_score` 是 `(1 + cos) / 2`，而 kNN 请求的 `similarity` 参数（现有 0.45）用的是原始余弦值。`searchWithScores` 必须换算 `cos = 2 × _score − 1` 后返回，本文中的 0.45、0.55、0.50 都是余弦值。不换算的后果已实测：问「今天中午吃什么」，最相关 3 个片段的 `_score` 为 0.64–0.66（余弦只有 0.28–0.32），直接拿 `_score` 比 0.55 会全部通过。
4. **组装提示词**：系统指令沿用 `COURSE_QA` 模板；附最近 3 轮对话（不含本轮，即最多 6 条已完成的消息，每条截断到 800 字；失败与已停止的回答不带入）；最后是本轮【课程资料】与【问题】。
5. **流式生成**：新增 `LlmService.chatStream(messages)`，调用 Ollama `/api/chat`（`stream:true`、`think:false`、`num_predict` 1024），每个返回块转为一个 `delta`。客户端断开时 MVC 在下一次写出时发现（生成期间写出间隔约几十毫秒），取消订阅并关闭到 Ollama 的连接，模型随即停止生成。
   - **跨块过滤 `<think>`**：现有的 `THINK_BLOCK` 正则只能处理完整文本，流式下标签可能被拆在两个块里。改为一个跨块的状态过滤器：遇到 `<think>` 后暂停下发，直到出现 `</think>`；块末尾若是 `<think>` 的不完整前缀（如 `<thi`），先暂存，与下一块拼起来再判断。保存到数据库的回答同样是过滤后的文本。
6. **完成后**：计算推荐（4.4）→ 保存 AI 消息（内容、引用、推荐 ID 与分数、耗时）→ 发送 `done`。占位由流的结束钩子统一释放（4.6）。

### 4.4 推荐算法

1. **选课**：候选片段按 `courseId` 分组（无课程归属的通用资料如《平台学习指南》只参与回答，不参与推荐），课程得分 = 组内最高片段的余弦值。保留得分 ≥ **0.55** 的课程，最多 3 门，按得分降序。门槛高于回答检索的 0.45：资料可以「有点相关」，推荐的课必须「明确相关」。参照基线：与课程无关的「今天中午吃什么」，最高余弦约 0.32。
2. **课程状态与可播放性**：课程服务新增内部接口 `POST /course/inner/outlines`，入参 `{ userId, admin, courseIds }`，返回每门课的概况（标题、封面、价格、是否已购、是否可试看）和课时列表（含 `playable`）。未上架或已删除的课不返回。内部调用校验方式与 `/order/inner/purchased` 相同。
   - **不能直接调用现有的 `LessonAccessPolicy` 方法**：`canStudyAll(course)` 与 `mask(course, lessons)` 从**当前请求头**读取身份，而 AI 服务的内部调用不带学生的请求头，`userId` 会是 null，所有付费课都会被判为未购买（不报错，只是结果错误）。
   - 改法：给 `LessonAccessPolicy` 增加接收显式身份的重载 `canStudyAll(course, viewer)`、`mask(course, lessons, viewer)`，`viewer = (userId, admin)`；现有两个方法改为用当前请求头构造 `viewer` 后委托给重载。判定规则（免费课、管理员、本课教师豁免、试看前 N 节、购买查询失败按未购买）仍只维护一份。
   - `outlines` 用请求体里的 `userId`、`admin` 构造 `viewer`；这两个值由 AI 服务在 4.3 第 1 步从请求头取得。
3. **选课时**：用第 3 步的问句向量与各课时标题向量计算余弦相似度，每门课取最高的 2 个且 ≥ **0.50**；都不达标时只显示课程卡片、不标课时。课时标题向量放在内存 LRU 缓存（键为课时 ID + 标题，上限 1000 条），标题变更即自然失效。
4. **故障隔离**：课程服务或订单服务失败时推荐为空并记录错误日志，回答照常完成。

两个门槛为初值（均为余弦值）；一期实现时用 `ai-reco-check.sh`（7.2）对 5.3 节的验收问题实测校准，最终取值与实测分数回填到本节。

**实测校准（2026-10-20，qwen3-embedding:0.6b，本机 ES，17 个分片；结论：维持 0.55 / 0.50）**

5.3 节验收问题（课程分 = 命中片段最高余弦；课时分 = 问句与课时标题的余弦，列出前 2）：

| 提问 | 课程分 | 课时分（前 2） | 结果 |
|---|---|---|---|
| HashMap 为什么线程不安全 | 2006 **0.785**、2007 **0.689**、2005 0.542 | 2006：4018 0.686、4019 0.651；2007：4024 0.734、4022 0.672 | 推荐 2006、2007 ✓ |
| 线程池参数怎么设 | 2007 **0.746** | 4025 0.775、4021 0.547 | 推荐 2007 ✓ |
| String 为什么是不可变的 | 2005 **0.745**、2007 0.462、2006 0.454 | 4015 0.843、4011 0.516 | 推荐 2005 ✓ |
| Vue 3 组合式 API 怎么组织页面逻辑 | 2002 **0.744**（已下架） | — | 由大纲接口按下架过滤 |
| 今天中午吃什么 | 无片段达到 0.45 | — | 不推荐 ✓ |

扩大样本（12 个问法）：8 个 Java 问题中 7 个期望课程 ≥ 0.62；真正无关的问题最高为「Redis 缓存击穿怎么处理」→ 2007 0.500，其余（简历、Python、MySQL 索引）无片段达到 0.45。据此：

- **课程门槛维持 0.55**：降到 0.52 会让「HashMap 为什么线程不安全」多推一门不相关的 2005（0.542），且离无关问题的 0.500 只差 0.02。
- **已知漏推**：「try-with-resources 怎么用」→ 2005 只有 0.531。原因是 2005「异常与常用类」一章的资料以 String 为主、异常内容在后半段，稀释了相似度；属于资料覆盖问题，不靠调门槛解决。
- **课时门槛 0.50 只是兜底，区分主要靠「每门取前 2」**：推荐课程内，不相关课时的标题余弦可达 0.65（「ArrayList 是怎么扩容的」与「HashMap 扩容机制与树化」，因「扩容」一词重合），高于相关课时的最低值 0.558，任何门槛都分不开；排序能把真正相关的课时放在前面。
- **用验收脚本复测（`scripts/local/ai-reco-check.sh`，与上表同一批数据）**：五个用例的分数与上表一致；经网关走真实流式对话，
  首字 0.09–0.15 秒、回答结束到推荐出现 0.01–0.12 秒（目标 1.5 秒 / 0.5 秒）。冷启动（模型尚未加载进显存）时第一次提问
  首字可达 1.5 秒以上，脚本先预热两次再计时。
- **余量偏小的用例**：「HashMap 为什么线程不安全」中 2005 为 0.542，距门槛 0.008。资料改动后要用 `ai-reco-check.sh` 复测。

### 4.5 历史中的推荐卡片

`ai_message.recommendations` 只存 `[{courseId, score, lessonIds}]`，不存价格、购买状态等会变化的信息。打开历史会话时，收集该会话全部推荐的课程 ID，调用一次 `outlines` 批量解析：学生买课后重新打开会话，卡片显示「已购」；已下架的课不再显示。

### 4.6 其他约束

- **同一用户同时只能有一个回答在生成**（本地模型只有一块 GPU，排队会相互拖慢）：第二个请求返回 409「上一个回答还在生成」。占位与释放的时机：
  - 在 4.3 第 1 步的第 4 小步原子占位，占位前不写任何数据；
  - 流开始前出现任何异常，立即释放；
  - 流开始后，无论以 `done`、`error` 结束还是客户端断开，都在流的结束钩子（`doFinally`）里释放，只释放一次。

  一期用 AI 服务进程内的集合实现，见 9 风险。
- **超时**：首个返回块 30 秒内未到达即中断；总生成时长沿用现有 `ai.llm.chat-timeout-seconds`（90 秒）；AI 服务的 MVC 异步超时为 120 秒，大于总生成时长。
- **时延目标**（M5 Pro、模型已加载）：首字 ≤ 1.5 秒；回答结束到推荐出现 ≤ 0.5 秒。

|---|---|---|
| 全新环境 | `db-init.sh`：`ai_schema.sql` 增加两张新表；`course_seed.sql`、`ai_seed.sql` 增加 Java 课与 8 篇资料 | 索引不存在或为空时，启动时全量回填（现有逻辑） |
| 已有数据的环境（含本机、服务器） | 执行增量脚本，可重复执行：<br>`zhixue-ai/.../sql/upgrade/2026-10-20-ai-conversation.sql`：新表用 `CREATE TABLE IF NOT EXISTS`，8 篇资料与分片用 `INSERT IGNORE`<br>`zhixue-course/.../sql/upgrade/2026-10-20-java-courses.sql`：3 门课、8 章、15 课时用 `INSERT IGNORE` | 见下 |

**启动时补齐未入索引的分片**：`KnowledgeIndexInitializer` 现在只在「索引不存在 / 维度不一致 / 索引为空」时回填。索引已有数据时，增量脚本新插入的分片永远不会被向量化，推荐用例中的前 3 个会全部失败。增加一条规则：索引存在、维度一致且非空时，查出 `es_id IS NULL`（且所属文档启用、未删除）的分片，批量向量化并写入，再回写 `es_id`。

- 分片按 `chunkId` 作为 ES 文档 ID 写入，写入成功后回写 `es_id`（现有 `KnowledgeBaseServiceImpl` 已是这样处理）。因此这一步可以重复执行，没有副作用；没有待补分片时只是一条空查询。
- 回填失败只记错误日志，不阻止启动（与现有初始化逻辑一致），下次启动再补。

## 6. 异常处理与安全

### 6.1 异常处理

原则：失败如实告知，不伪装成回答；推荐失败不影响回答；内部细节（模型名、地址）只进日志。

表中「后端」一列的 400 / 404 / 409 指 `body.code`（HTTP 200），401 为网关返回的 HTTP 401，503 / 504 为 `error` 事件里的 `code`，见 4.2。

| 场景 | 后端 | 学生看到的 |
|---|---|---|
| 未登录 / 令牌过期 | 流开始前，网关返回 HTTP 401 | 跳登录页，回来后问题仍在输入框 |
| 问题为空或超过 500 字 | 400（前端发送前也校验） | 输入框下方提示，不发送 |
| 会话不存在或非本人 | 404 | 「会话不存在或已删除」，刷新「最近」 |
| 已有回答在生成 | 409（占位失败，此前不写任何数据） | 「上一个回答还在生成」，发送按钮暂不可用 |
| 占位后、流开始前出错（如保存消息失败） | 释放占位，返回 500 | 「发送失败，请重试」，问题仍在输入框 |
| 本地模型不可用 | `error` 503，回答存为失败 | 红色失败气泡「AI 服务暂不可用，请稍后再试」+「重试」 |
| 首个返回块 30 秒未到 | `error` 504 | 「AI 响应超时」+「重试」 |
| 已出字但超过 90 秒 | 已生成部分存为失败 | 保留文字，末尾「生成超时，已中断」 |
| 资料检索失败（ES 不可用） | 不带资料回答，不出推荐，`done.notice` 说明 | 回答下方灰字「课程资料暂时无法检索，本次回答未参考课程资料」 |
| 推荐计算失败 | 推荐为空，记错误日志 | 不显示推荐区 |
| 学生点「停止」 | 取消模型请求，部分内容存为已停止 | 保留文字，标「已停止」 |
| 网络中途断开 | 按停止处理 | 「连接中断」+「重试」；重开会话显示服务端保存的结果 |
| AI 服务重启导致问题无回答 | — | 历史中该问题下显示「此问题未完成回答」+「重试」 |
| 历史卡片的课程已下架 / 删除 | 不返回该卡片 | 卡片不显示 |
| 打开历史时课程服务不可用 | 消息照常返回，卡片为空 | 历史可读，无卡片 |

### 6.2 内容安全

- Markdown 渲染禁用原始 HTML（`markdown-it` 的 `html:false`），渲染前不再拼接任何未转义内容。
- 图片不加载，只渲染为链接文本（防追踪像素）。
- 链接仅允许 `http/https`，新窗口打开，`rel="noopener noreferrer nofollow"`。
- 过滤模型输出中的 `<think>` 段：流式下用跨块状态过滤器（见 4.3 第 5 步），不能只沿用现有的整段正则。
- 课程资料与学生问题只作为文本交给模型，系统指令声明其不是指令（沿用现有提示词约束）。

|---|---|---|
| 「生成中」登记在单个 AI 服务实例内存中 | AI 服务多实例部署时并发限制失效 | 多实例前改为 Redis `SET NX` + 过期时间 |
| 推荐精度依赖知识库资料质量 | 资料单薄的课程推荐不出来 | 种子资料按章编写；精度不足时升级为「检索 + 模型确认」（D7） |
| 课时只有标题可用于匹配 | 课时标注可能不准 | 课时门槛 0.50，达不到只显示课程卡片；三期如需可为课时增加简介字段 |
| 示例视频为同一段公共视频 | 演示中各课时播放内容相同 | 仅用于种子；替换真实视频只改 `video_url` |
| 本地单 GPU 吞吐有限 | 多名学生同时提问需排队 | 每人限 1 个进行中的回答；Ollama 自身排队；超时如实提示 |
| 以后部署到服务器 | 本设计的模型与时延目标都基于本机 M5 Pro，服务器跑不动该模型；经 Nginx 代理时 SSE 默认会被缓冲 | 部署前需另行确定模型的运行位置；SSE 已带 `X-Accel-Buffering: no`，Nginx 无需改配置 |

## 10. 术语

| 术语 | 含义 |
|---|---|
| 会话 | 一组连续的问答，对应侧边栏「最近」中的一项 |
| 课程资料 / 片段 | 知识库文档及其切分后的检索单元（`kb_document` / `kb_chunk`） |
| 推荐卡片 | 回答下方的课程推荐，含最多 2 个标注课时 |
| 可播放（playable） | 已购买，或处于课程允许的试看范围内 |
| 流前错误 | 开始推送事件流之前即可判定的错误，以普通 JSON 返回 |
| 余弦值（cos） | 本文所有相似度门槛的刻度；ES `_score` 需按 `cos = 2 × _score − 1` 换算 |
| 占位 | 「生成中」标记，保证同一用户同时只有一个回答在生成 |
